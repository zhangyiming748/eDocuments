# eDocuments

纸质档案数字化：把扫描件图片在本地完成 OCR 识别，文本存入 Elasticsearch，提供一个简单的中文全文搜索页面。全程离线运行，扫描件不出本机。

# 大纲

1. 全部编程语言使用 Go。
2. Elasticsearch 运行在 Docker 上，单节点即可，作为唯一的数据库与全文搜索工具，数据通过数据卷持久化到硬盘。
3. 文档以**扫描图片**形式存储在硬盘上：用户提供一个根目录，根目录下每一个**最终目录**（不含子文件夹、只包含图片文件的目录）算作一份文档，**文件夹名即文档标题**。
4. OCR 在**本地**完成，使用 Tesseract 5（语言包 `chi_sim` 为主、`eng` 为辅，处理少量英文专有名词），不调用任何在线 OCR 服务。识别对象以中文为主。
5. OCR 识别结果以 **JSON 文件**形式缓存在本地磁盘（每份文档一个 JSON），同时写入 Elasticsearch 实现全文搜索。重建 ES 索引时直接读缓存，不重复 OCR。
6. 提供一个简单的搜索页面：输入关键词，返回相关文档的**标题与正文高亮片段**（无需对照原图、无需页码跳转）。
7. 图片页序规则：扫描设备导出为 `scan_0001.jpg` 这类**定宽零填充顺序命名**，按文件名升序即为页序；不要求每份文档都从 0001 开始，起始编号任意，顺序正确即可。
8. 支持图片格式 jpg/jpeg/png/tif/tiff（扩展名大小写不敏感）；目录中的非图片文件忽略并记录警告；空目录跳过。
9. 文档唯一 ID 为**相对路径的 SHA-256 哈希**，不同年份/类目下的同名文件夹不会冲突；文件夹名仅作为标题。
10. Elasticsearch 安装 **IK 中文分词插件**（插件版本与 ES 版本严格一致，使用自定义 Dockerfile 构建 ES 镜像）：索引分词 `ik_max_word`，搜索分词 `ik_smart`。
11. 规模约每年 300 页，全量 OCR 耗时为分钟级，不需要任务队列；一个索引命令顺序/小并发跑完，支持基于文件 mtime+size 的增量更新、删除同步与失败页报告。
12. 部署形态为**纯单位局域网内访问**，不做内网穿透、不绑定公网域名、不设用户名密码（信任边界即单位局域网）；同事通过 `http://<服务器内网IP>:8080` 直接访问搜索页。Elasticsearch 端口不对宿主机暴露，仅 Docker 内部网络可达；部署机器内存 16～64GB，ES 堆内存固定 1GB。

# 实现方案（项目介绍）

## 总体架构

两个容器，由 docker-compose 编排：

```
扫描根目录(挂载为只读卷)
        │
        ▼
┌─────────────────────────────┐
│ edocs 容器（Go 单二进制）      │
│  · tesseract 5 系统命令        │
│  · 子命令 index：扫描→OCR→入库 │
│  · 子命令 serve：搜索 Web 服务 │
└──────────┬──────────┬───────┘
           │          │
           ▼          ▼
  OCR 结果 JSON 缓存目录   Elasticsearch 8（单节点）
  （绑定挂载 ./data/cache） （IK 插件 + 命名卷 es-data）
```

- Go 程序通过 `os/exec` 调用容器内的 `tesseract` 命令行，避免 CGO 交叉编译问题。
- Go 服务同时承担两个角色：离线索引器（`index`）与在线搜索服务（`serve`），由子命令区分。
- Web 页面用 Go 标准库 `net/http` + `html/template` 内嵌渲染，不引入前端框架、不做前后端分离。

## 为什么选择 Elasticsearch 而非 SQLite（选型说明）

本项目数据规模很小（每年约 300 页，单机内网使用）。若仅看规模，SQLite + FTS5（trigram 分词）已经够用：无需独立服务、备份只是一个文件、查询同样是毫秒级。最终仍选择 Elasticsearch，理由集中在**中文检索质量与容错能力**，而非数据量：

1. **中文分词生态成熟**：ES 有 IK Analyzer（`ik_max_word`/`ik_smart`）、可配置自定义词典（人名、机构名、专业术语），并支持索引期与查询期使用不同分析链；SQLite FTS5 没有中文分词器，只能在建库前由程序预先分词写死，同义词、停用词、拼音等分析能力基本空白。
2. **OCR 错字的容错搜索**：档案 OCR 文本必然存在错字（如"财务"被识别成"财物"）。ES 原生支持编辑距离模糊查询（fuzziness）、短语纠错与搜索建议，用户输错一个字或原文认错一个字仍能命中；FTS5 仅有前缀匹配与 NEAR 邻近查询，没有真正的容错匹配，trigram 的"鲁棒性"只是共享三元组带来的副作用，排序不可控。
3. **相关性与高亮能力更完整**：ES 的 BM25 支持多字段权重（标题命中加权）、组合查询与重打分，未来加筛选、聚合统计时无需换引擎；FTS5 的 `bm25()`/`snippet()` 能满足基础需求，但扩展天花板低。
4. **为未来扩容与学习留出空间**：数据增长到数十万页、多人并发使用，或需要分面筛选、同义词、拼音搜索时，ES 无需迁移；同时也借此项目掌握一套主流的检索技术栈。

代价是已知并接受的：多维护一个 JVM 容器、IK 插件版本必须与 ES 版本严格对应、占用 1GB 以上内存（部署机内存 16～64GB，可接受）。

为保留退路，代码中 `store` 层定义为接口（`Index`/`Delete`/`Search`）：当前实现 ES 后端；若将来确认用不到上述能力，可补一个 SQLite FTS5 实现，OCR、JSON 缓存与 Web 层无需改动。

## 文档发现与页序

1. 递归遍历扫描根目录，找出所有"叶子目录"（目录内无任何子目录）。
2. 在叶子目录中收集受支持的图片文件，按文件名升序排列即为页序；`scan_0001`、`scan_0002` 这种零填充命名下，字典序与数字序一致。
3. 防御性校验：解析文件名中的数字部分，若出现非唯一或非递增的异常情况（例如混入两套命名），输出警告，提示人工检查，避免静默排错页。
4. 非图片文件（`.DS_Store`、扫描仪缩略图等）忽略并告警；空叶子目录跳过并告警。
5. 文档 ID = 相对根目录路径的 SHA-256；标题 = 文件夹名；同时保存相对路径字段以备将来按年份/类目过滤。

## OCR 处理

- 运行时：Debian slim 基础镜像，`apt install tesseract-ocr tesseract-ocr-chi-sim tesseract-ocr-eng`，语言包随镜像打包，保证纯离线可用。
- 预处理：按 EXIF 方向自动旋转；必要时转灰度（Tesseract 内部也会做二值化）。档案扫描建议 300 DPI，过低分辨率会明显影响识别率。
- 并发：小并发 worker 池（默认 2，可配置），Tesseract 为 CPU 密集任务，避免并发过高。
- 质量标记：通过 Tesseract TSV 输出获取每页平均置信度，写入 JSON，低于阈值（如 70）的页在索引报告中列出，供人工抽查。
- 单页失败不中断整批：记录失败文件名与错误信息，跳过该页继续，全部结束后输出失败页汇总。

## OCR 结果 JSON 缓存

缓存目录下每份文档一个文件，文件名为文档 ID，示例：

```json
{
  "id": "a1b2c3...（相对路径的 sha256）",
  "title": "某某档案",
  "relative_path": "2024/综合类/某某档案",
  "page_count": 12,
  "ocr_finished_at": "2026-10-18T10:00:00+08:00",
  "pages": [
    {
      "file": "scan_0001.jpg",
      "size": 1048576,
      "mtime": "2026-09-01T08:30:00+08:00",
      "text": "本页识别出的全文……",
      "avg_confidence": 93.4
    }
  ]
}
```

缓存同时充当断点记录与备份：ES 数据卷损坏时，仅凭缓存目录即可完整重建索引。

## Elasticsearch 索引设计

索引 `documents`，单文档即一份档案，正文为各页文本按页序拼接：

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | `text`，`ik_max_word`，附 `keyword` 子字段 | 文档标题（文件夹名） |
| `content` | `text`，索引 `ik_max_word` / 搜索 `ik_smart` | 全部页的 OCR 文本，页与页之间换行分隔 |
| `relative_path` | `keyword` | 相对路径，预留按年份/类目过滤 |
| `page_count` | `integer` | 页数 |
| `indexed_at` | `date` | 最近一次入库时间 |

文档 `_id` 直接使用相对路径哈希，保证重复索引是覆盖而不是产生重复文档。搜索采用两阶段策略：先用 `simple_query_string`（支持多关键词/短语）精确检索；精确零结果时自动退到 `multi_match` + `fuzziness: AUTO:2,5` 容错检索，以召回 OCR 错字或用户输入差一个字的文档（2～4 字词容忍 1 字之差），精确命中时则不混入模糊噪声。开启 ES 原生 `highlight`，标题与正文片段以 `<em>` 高亮返回；结果分页展示。

## 索引与增量策略

`edocs index --root /data/scan` 执行流程：

1. 扫描根目录得到全部文档及其页文件（mtime+size）。
2. 对每份文档：
   - JSON 缓存存在且所有页未变化 → 跳过 OCR；
   - 新增或有页变化 → 仅对变化的页重新 OCR，更新缓存；
   - 扫描后已消失的文档 → 删除其 ES 文档与 JSON 缓存。
3. 将缓存内容批量写入 ES（按 `_id` upsert）。
4. 输出汇总：新增/更新/跳过/删除文档数、失败页与低置信度页清单。

另提供两个开关：`--reindex` 只读缓存全量重建 ES（不重新 OCR）；`--force-ocr` 忽略缓存全部重新识别。

## 搜索页面

- `GET /`：搜索框页面。
- `GET /search?q=关键词&page=1`：结果列表，每条包含标题（命中高亮）、正文高亮片段、页数；无结果时给出提示。
- 服务监听 `0.0.0.0:8080`，仅供内网访问。

## Docker 部署细节

- ES 镜像：基于 `elasticsearch:8.x` 自定义 Dockerfile 安装版本匹配的 `analysis-ik` 插件。
- ES 配置：`discovery.type=single-node`、`xpack.security.enabled=false`（纯内网简化部署）、`ES_JAVA_OPTS=-Xms1g -Xmx1g`；数据由命名卷 `es-data` 持久化（ES 数据为容器私有、随机 I/O 密集，不适合绑定挂载）；磁盘水位放宽到 90%/95%/97%，避免单节点在宿主机磁盘偏紧时拒绝分配分片；ES 端口只在 compose 内部网络可见，不映射到宿主机。
- 网络边界：仅 Go 服务的 8080 端口映射到宿主机，供局域网访问；不配置任何内网穿透。宿主机防火墙建议只放行局域网网段的 8080，拒绝其他来源；服务器本身不要直接暴露在互联网上。
- edocs 镜像：多阶段构建，Go 编译产物放入含 Tesseract 与中文语言包的 slim 镜像；扫描根目录以只读卷挂载到 `/data/scan`，OCR JSON 缓存**绑定挂载**到宿主机 `./data/cache`（普通文件，便于直接抽查与备份，`.gitignore` 已忽略）。
- 典型使用：

```bash
docker compose up -d elasticsearch          # 启动 ES（首次会等待健康检查通过）
docker compose run --rm edocs index --root /data/scan   # 全量/增量索引
docker compose up -d edocs                   # 启动搜索服务
# 浏览器访问 http://<本机内网IP>:8080
```

## 规模与资源预估

- 每年约 300 页，全量 OCR 预计数分钟到半小时（取决于扫描清晰度与机器 CPU）。
- ES 堆内存固定 1GB，在 16～64GB 内存的机器上资源充裕；OCR worker 默认 2 并发，可按 CPU 核数调整。
- 数据安全重点备份两处：扫描根目录原件与 `/data/cache` 下的 JSON 缓存；ES 数据卷可随时由缓存重建。
